# The Chancellor — Commercial v1 Go-Live Checklist

This is the final operational gate for paid public traffic. The application should be treated as **code-complete v1** only when CI is green, and **live-ready** only when `/api/go-live` reports `readyForPaidTraffic: true` on the production Render service.

## 1. Render production configuration

Confirm these secret environment variables in Render:

- `ADMIN_EMAIL`
- `ADMIN_PASSWORD` — minimum 12 characters; use a unique strong password
- `OPENAI_API_KEY` — optional for AI/voice; the site has fallback behaviour
- `PAYFAST_MODE=live` only after sandbox testing is complete
- `PAYFAST_MERCHANT_ID`
- `PAYFAST_MERCHANT_KEY`
- `PAYFAST_PASSPHRASE` — required for recurring Professional Network memberships
- `RESEND_API_KEY` and `COMMS_FROM_EMAIL` if email notifications are enabled
- Twilio credentials only if SMS/WhatsApp is enabled
- `ADMIN_ALERT_EMAIL` / `ADMIN_ALERT_PHONE` where operational escalation is required

`SESSION_SECRET` is generated by Render from `render.yaml`. `APP_URL` must remain the production HTTPS URL.

## 2. Payment acceptance tests

Before switching PayFast to live mode, complete sandbox tests for:

1. R500 Growth Desk audit checkout and ITN confirmation.
2. Professional Network recurring monthly membership checkout and renewal ITN.
3. Rescue Case professional fee deposit.
4. Rescue Case full-balance payment.
5. Duplicate ITN handling.
6. Incorrect amount / merchant / signature rejection.
7. Professional payout cannot be marked paid before the client invoice is fully settled.

Never treat a browser return URL as proof of payment. The stored payment state must come from validated PayFast ITN processing.

## 3. Operational access tests

Test each role in a private browser session:

- Growth Desk client
- Rescue client
- Professional Network member
- Firm / practice principal
- Referral partner
- Institutional account
- Chancellor administrator

Confirm that each role can see only its own authorised data.

## 4. Rescue and professional controls

Before onboarding paid Rescue cases:

- Verify professional credentials against the relevant regulator / professional source.
- Mark the professional Verified only after evidence review.
- Require current paid membership or an explicit administrator subscription override.
- Confirm speciality, jurisdiction and availability before manual assignment.
- Do not use the Chancellor Performance Score as a substitute for regulatory eligibility.
- Review critical unassigned cases from the Command Centre every operating day.

## 5. Public proof and marketing

- Publish only client-confirmed aggregate outcomes.
- Publish success stories only after anonymisation and administrator approval.
- Publish testimonials individually; do not infer consent from a private rating.
- Publish professional profiles only after explicit platform approval and verified status.
- Do not claim guaranteed debt reduction, tax relief, funding, tenders, legal outcomes or investment returns.

## 6. Referral and institutional controls

- Referral commissions remain disabled unless deliberately authorised.
- Review legal/professional-body restrictions before paying commissions for regulated professional referrals.
- Record referral payouts with a payment reference.
- Institutional packages are contract/SLA driven; confirm commercial terms before activation.
- Share institutional benefit codes only with eligible beneficiaries.

## 7. Data and privacy operating controls

- Keep `/app/data` on the persistent Render disk and retain one application instance while using the JSON store.
- Establish an encrypted off-platform backup routine for business-critical records before meaningful volume.
- Do not store card details, PINs or passwords in case notes or uploads.
- Limit uploaded identity, legal and financial records to information needed for the service.
- Establish internal retention/deletion procedures and obtain South African privacy/legal review before large-scale launch.

## 8. Hard scaling boundary

The current `store.js` is a single-file JSON datastore with atomic file replacement. It is appropriate only for a controlled single-instance v1 launch. **Do not increase Render `numInstances` above 1 and do not operate high concurrent transaction volume on this datastore.**

Before horizontal scaling or material enterprise volume, migrate transactional data to a managed database (for example PostgreSQL), migrate file metadata and access controls, add database backups, migrations, transactional locking/idempotency constraints, and then load-test the full payment/case workflow.

## 9. Final technical gate

1. GitHub Actions `Chancellor v1 CI` must be green on the exact commit being deployed.
2. Render deployment must report healthy at `/api/health`.
3. `/api/features` must show the required v1 modules mounted.
4. `/api/go-live` must return `readyForPaidTraffic: true`.
5. Open the public homepage, Rescue page, Results & Trust, Partner Portal and Institutional Accounts on desktop and mobile.
6. Sign into the Command Centre and verify CEO, Rescue, Professional, Firms, Revenue, Outcomes, Public Proof, Referrals, Institutional and Communications views.

Only after these checks should paid traffic and external institutional sales be treated as production launch activity.
